# Mission 002: note judgment

## Three different clocks

1. **Chart timestamps** are generated by the unchanged converter:
   `tick = int((chart_tick / resolution) * 3567673)`. The supplied chart uses
   resolution 192, initial BPM value 83330 (thousandths), and 699 ordered notes.
   Generated notes retain the verified 16-byte layout from Mission 001.
2. **Gameplay time** is `VBlank frame count × initial BPM value`. GBA hardware
   supplies 16777216 clock cycles/second and 280896 cycles/frame, approximately
   59.7275 frames/second. The interrupt increments a 32-bit frame counter; the
   main thread snapshots it and multiplies using 64-bit arithmetic. Judgment
   uses the existing chart-clock units, not raw `.chart` ticks or milliseconds.
3. **Audio playback time** belongs to Maxmod's module player. `mmVBlank`,
   `mmFrame`, module data and looping remain unchanged. Judgment does not seek,
   mute, query or control audio. It is a frame-based approximation of song time,
   not a sample-position clock. The original empirical conversion and potential
   audiovisual drift have not been recalibrated.

Mission 001 advanced the same song clock in VBlank and checked the previous
keyboard poll. Mission 002 polls input first and makes all judgments on the main
thread. This removes the extra stale-input delay and avoids a torn 64-bit clock
read. The original position formulas and pre-increment ten-frame sprite
lookahead remain. The camera/highway and music are not redesigned.

## Timing windows

These are explicit initial gameplay tolerances expressed in real time, not BPM
counts guessed to mean milliseconds. They are not a claim of human calibration.

| Result | Timing relative to the note |
| --- | --- |
| Perfect | At most 25 ms early or late |
| Good | Outside Perfect, but at most 50 ms early or 85 ms late |
| Missed | Still pending after the 85 ms late boundary |

Boundaries are inclusive. Window conversion first rounds microseconds down to
GBA CPU cycles, then to chart-clock ticks. For the demo: Perfect is 124427 ticks,
early Good 248854 ticks, late Good 423052 ticks. Rounding error is below one
microsecond; input itself is sampled approximately every 16.74 ms. The old
three/five-frame windows were about 50.23/83.71 ms; the new allowance is close,
but intentionally explicit. Perfect is a new classification.

## State and input rules

Each individual note starts Pending and can transition exactly once to Perfect,
Good or Missed. The engine keeps one byte of state per note. Hit totals are
Perfect + Good; judged total is hits + misses and cannot exceed the note count.
There are no score points, multipliers or streak mechanics in this mission.

The physical button order, from left to right, is **D-pad Left, D-pad Right, A,
B**, overriding the older controls in the attached mission brief. One shared
mapping drives both judgment and the existing fret animations. Other buttons
(Up, Down, L/R shoulders, Start and Select) are not gameplay lane inputs.

- Supply held lane bits to `step(now, heldLanes)`. The engine derives newly
  pressed edges; holding a key cannot automatically hit later notes.
- Each new lane press hits at most the earliest eligible Pending note in that
  same lane. Repressing an already judged note cannot award it again.
- Chords consist of individual notes. Pressing the chord together judges all
  matching members. Partial chords can be completed with fresh presses within
  their windows; unplayed members become misses. Holding one member does not
  retrigger it. The current demo contains no chords, so synthetic host tests
  exercise these cases.
- Extra/unrelated buttons do not invalidate a correct hit or consume another
  lane's note. Valid notes receive hits and unmatched presses produce a separate
  WrongInput event. One input poll groups its unmatched lane bits into one event.
- Too-early input is WrongInput and leaves the note pending. Too-late input can
  produce both the note's one automatic Miss and a separate WrongInput. Neither
  case increases the miss counter twice. No input still produces automatic misses.
- `reset(heldLanes)` clears states, counters and edge history while retaining
  the event subscription. Supplying already-held bits prevents a phantom new
  press at reset. Reset is tested in isolation; no in-game restart menu is added.

A physical GBA D-pad normally cannot hold Left and Right together, and emulator
frontends may filter opposing directions. The engine accepts such a chord's
lane bits, but this mapping is not physically suitable for future Left+Right
chords. The supplied chart has none. Do not silently remap or change chart data.

## Events and presentation

`include/noteJudgment.hpp` contains the hardware-independent engine.
`setEventSink(callback, context)` subscribes a single synchronous callback to:

- `PerfectHit` and `GoodHit`: one event per successfully judged note.
- `Miss`: one event per expired unplayed note.
- `WrongInput`: one event per poll containing unmatched new presses.

Each event includes a note index, lane mask, chart timestamp and observed
gameplay timestamp. WrongInput uses `NO_NOTE`, chart timestamp zero and the
unmatched lane mask. Event timestamps use the clock units described above;
these are not audio sample positions. Expired misses are emitted before hits,
then remaining wrong presses. No event queue can overflow or drop chord members.
Callbacks must be short and must not reenter `step` or reset the engine.

`NoteManager` retains note-position preparation and sprite lookahead. It owns the
judgment engine but no text renderer. `source/main.cpp` consumes events for a
minimal HUD: latest PERFECT/GOOD/MISS, `H:` hits, `M:` misses and a separate WRONG
flash lasting 24 frames (about 0.40 seconds). The old Streak display is replaced,
not turned into a scoring system. Existing font tiles render the labels. Each
label is bounded to 16 sprite entries, separate from the 32 note sprites.

The sprite loader derives hit appearance from the note's persistent state, so
reloading a visible sprite does not undo successful-hit feedback. Automatic
misses leave the original note artwork moving down the highway.

## Tests and assumptions

Run `bash tests/check.sh` on a computer with GCC and Python 3. AddressSanitizer,
UndefinedBehaviorSanitizer and leak detection stay enabled. Tests cover exact
and boundary hits, early/late input, no-input misses, wrong/extra input, chords,
partial chords, held buttons, duplicate attempts, reset, final/empty charts,
requested control mapping, tempo-independent real-time windows, and two complete
699-note runs. Every note's event count and final statistics are checked.

For actual ROM testing on Debian with `gcc` and `libmgba-dev`, build the ROM and
set `DEVKITARM`, then run:

```bash
bash tests/run_emulator.sh perfect /tmp/perfect.ppm
bash tests/run_emulator.sh miss /tmp/miss.ppm
bash tests/run_emulator.sh mixed /tmp/mixed.ppm
```

Each scenario runs 36000 frames, checks final/per-frame counters, framebuffer
changes, nonzero audio samples and no core crash. It uses symbols from the
matching ELF, not hardcoded RAM addresses. The tests inject raw core button bits;
they do not test a frontend's keyboard mapping or opposing-direction filter.

The supported chart must be sorted by timestamp, have lanes 0–3 and a positive
constant BPM. Tempo changes, arbitrary malformed data, sustain gameplay and
multi-hour playback are not qualified. See `MISSION_002_RESULTS.md` for measured
results and the manual-play limitations.

## Mission 003 integration point

Reactive audio can consume the existing events in the main-thread consumer (or
in a small dispatcher called by it), using note index, lane and timing as needed.
Do not put music-volume logic into `NoteJudgment`. Chords emit per-note events,
so decide explicitly whether audio should respond per note or per chord/frame.
Keep callbacks short; request audio changes for subsequent processing rather
than blocking judgment. Keep Maxmod as the playback owner and define audio-clock
alignment/latency policy before adding penalties. Mission 002 changes no music
content, volume or mixing behavior.
